Is useEffect a Code Smell?

"useEffect is a code smell" overstates a narrower point that holds up. This page sets out what effects are for, where the slogan comes from, and the words the lessons use. The lessons after it run each misuse next to its fix, so you can see the bugs happen and count them.

The short answer

Effects are the right tool for syncing with something outside React: subscriptions, timers, sockets, browser and DOM APIs, a network request that must follow the screen. They cause bugs when they become a general "when X changes, do Y" mechanism, in particular to compute derived state or to respond to something the user did.

A common reply to the slogan is that effect bugs only matter under heavy load. The lessons test that reply. Two of the four bugs happen every time, at any scale. The other two depend on the network and on how fast people type and click, and one user on a poor connection is enough.

Effects as "when X changes, do Y"

State changes, an effect notices, and the effect sets more state, sends a request or fires an event. Each effect looks reasonable alone. Together they make behaviour depend on the order and timing of renders, which the code does not show.

Effects for syncing, and nothing else

Values computed from props and state are computed during render. Things the user did are handled in the event handler. Effects remain for keeping React in step with an outside system, and every such effect has a cleanup.

Where the slogan comes from

  • The React docs' page "You Might Not Need an Effect". It lists specific misuses and their replacements. The title travelled further than the list.
  • Strict Mode in React 18 and later. In development, React mounts every component twice to expose effects that lack cleanup. People saw every request sent twice and blamed effects.
  • Dependency arrays. A missing dependency gives stale values; a dependency that changes every render gives an endless loop. The lint rule that checks them is a constant argument.
  • Data fetching moved elsewhere. Data libraries such as React Query, framework route loaders and server components took over most fetching. "Do not fetch in effects" drifted into "effects are bad".

Terms

Render
React calling your component function to work out what the screen should show. It should only calculate.
Commit
React applying the result of a render to the DOM. A commit can happen and be replaced before the browser paints it.
Paint
The browser drawing the DOM on screen. What the user sees.
Effect
A function passed to useEffect. React runs it after a commit, usually after the browser has painted.
Dependency array
The list after the effect. React runs the effect again when any value in it changes.
Cleanup
The function an effect returns. React runs it before running the effect again and when the component goes away.
Mount and unmount
A component appearing in the tree, and leaving it. Navigating away and back unmounts and mounts it again.
Derived state
A value that can be calculated from props or other state. Storing it in state and syncing it with an effect adds a render and a chance to be wrong.
Key
A prop that tells React which component instance is which. A new key throws the old instance and its state away.
Race condition
A bug that depends on which of two things finishes first. Here: which of two requests answers last.
Latency jitter
How much the time to answer varies from one request to the next. Mobile connections have far more than wired ones.
Debounce
Waiting until the input has been still for a while before acting on it, so a burst of keystrokes sends one request.
Waterfall
Requests that run one after another because each is started by the previous one finishing.

A working rule

If the effect talks to something outside React, keep it and give it a cleanup. If it only computes a value from props or state, compute it during render, with useMemo if it is expensive. If it reacts to something the user did, move it into the event handler.
