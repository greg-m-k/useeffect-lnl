So is it a code smell?

Two claims meet in this argument. One says "useEffect is a code smell". The other says the bugs it causes only matter under heavy load. The lessons measured both. This page puts the results together with the argument the lessons cannot measure: what effects cost the people who maintain the code.

The maintainability argument

Most critics of effects mean developer cost more than user cost, which is why the argument rarely comes with a failing user-facing test. A chain such as effect A sets state, which triggers effect B, which sets state, which triggers effect C, is hard to follow: its behaviour depends on the order and timing of renders, and none of that order is written in the code.

AI assistants change part of this. They can trace and explain an effect chain, so for small components the cost of understanding one is low. They share the human blind spot for timing-dependent interactions, they tend to reproduce effect-heavy patterns, and they often silence the dependency lint rule where a fix was needed. If AI makes maintaining effect chains cheap, it also makes removing them cheap.

Scorecard

What holds up

  • The slogan, as usually stated, is lazy.
  • Effects that sync with something outside React are the right tool.
  • The race needs specific conditions: jitter larger than the time between inputs.
  • For small, simple components the maintenance argument is weak.

What does not

  • "It only matters under heavy load." The race depends on jitter and input speed, and one user on a poor connection hits it.
  • "It is rare." Two of the four bugs, the stale reset and the repeated submit, happen every time.
  • "Rare per session" still adds up across many users.

At typical scale

How often the race happens is interactions per day multiplied by the odds per interaction. Company size says little about user count: a bank's internal tool might have 40 users and a ten-person startup a million. Take two examples, using the rates measured in How rare is the race?:

  • An internal tool: 50 users making 20 quick selections a day is 1,000 interactions. On a steady wired network the lesson sees no races at all; at 1 in 10,000 that would be one stale result every ten days. On office Wi-Fi with some jitter it measured around 1%, about ten a day, and still nobody files a ticket: the results look plausible and people type again.
  • Consumer search on mobile: a million interactions a day at a few percent is tens of thousands of stale results a day.

On frequency alone, the race is a scale problem, and for many apps a minor one. Two things do not scale with user count:

  • The cost of one occurrence. In an admin or records tool, the dangerous case is a detail pane whose header says customer B while the form holds customer A's data, and a save that writes A's data to B's record. In billing or medical software, one occurrence is expensive. Small apps are often exactly these tools.
  • The bugs that always happen. The stale commit after a reset and the order placed again after navigation happen in a tool with 50 users as often as in one with 50 million.

The verdict

"useEffect is a code smell" is an overstatement of a valid, narrower point. Effects are the right tool for syncing with something outside React. As a general "when X changes, do Y" mechanism they produce bugs, two of them every time, and the timing bugs depend on the network and on how fast people type and click.

For a typical small app, the race is a low-priority risk unless the screen edits records that matter. The cleanup is three lines, so it is worth writing anyway. It is not worth a long argument.

A working rule. If the effect talks to something outside React, keep it and always give it a cleanup. If it only computes a value from props or state, compute it during render, with useMemo if it is expensive. If it reacts to something the user did, move it into the event handler.

Further reading

  • You Might Not Need an Effect, the React docs. The page the slogan grew out of: each misuse in these lessons, with its replacement.
  • Code Smell, Martin Fowler. A smell is a surface sign that usually, though not always, points to a deeper problem. That is the useful reading of "useEffect is a code smell": look closer, then decide.
  • Data Fetching Patterns in Single-Page Applications, Juntao Qiu. Parallel data fetching, fallback markup, code splitting and prefetching, with the request waterfall from lesson 4 as the starting point.
  • Modularizing React Applications with Established UI Patterns, Juntao Qiu. Moving logic out of components into plain modules, which is where most "when X changes, do Y" code belongs.
  • Headless Component: a pattern for composing React UIs, Juntao Qiu. Keeping behaviour in hooks with a clear job, separate from rendering.
  • Eradicating Non-Determinism in Tests, Martin Fowler. How to test asynchronous behaviour without flaky timing, which is how the race test in lesson 1 controls the order of answers.
  • Self Testing Code, Martin Fowler. The habit that turns a timing bug into a failing test before it reaches users.
  • Definition Of Refactoring, Technical Debt and Is High Quality Software Worth the Cost?, Martin Fowler. The maintainability argument in general form: hard-to-follow code slows every later change.
